Three ways to make a game

Vertex has one engine and three ways of using it. Here's the same small thing (a cube that bobs up and down and spins) done each way, then how to mix them.

1. Code only

A game is a class with a Load method that builds the world. Start it from Main (here, a top-level statement) and it opens its own window.

using System.Numerics;

using Vertex;
using Vertex.Rendering;

new BobbingGame().Run("Bobbing cube");

public class BobbingGame : Game
{
    public override void Load()
    {
        var sun = new GameObject("Sun");
        sun.AddComponent<Light>();
        sun.Transform.EulerAngles = new Vector3(-50f, 30f, 0f);

        var camera = new GameObject("Camera");
        camera.AddComponent<Camera>();
        camera.Transform.Position = new Vector3(0f, 1f, 6f);

        GameObject.CreatePlane(Vector3.Zero, size: 20f);
        GameObject cube = GameObject.CreateCube(new Vector3(0f, 1f, 0f), Color.Orange);
        cube.AddComponent<Bobber>();
    }
}

/// <summary>Bobs up and down and spins.</summary>
public class Bobber : Component
{
    public float Height { get; set; } = 0.5f;
    public float Speed { get; set; } = 2f;

    private Vector3 _start;

    protected override void Start() => _start = Transform.Position;

    protected override void Update()
    {
        Transform.Position = _start + new Vector3(0f, MathF.Sin(Time.TotalTime * Speed) * Height, 0f);
        Transform.EulerAngles += new Vector3(0f, 90f * Time.DeltaTime, 0f);
    }
}

The project file is an ordinary .NET program that uses the engine's package (from the download; built from source, use <ProjectReference Include="..\Vertex\Vertex\Vertex.csproj" /> instead). Copying the Assets folder next to the program lets the game load files from it:

<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <OutputType>WinExe</OutputType>
    <TargetFramework>net10.0</TargetFramework>
    <ImplicitUsings>enable</ImplicitUsings>
    <Nullable>enable</Nullable>
  </PropertyGroup>
  <ItemGroup>
    <PackageReference Include="Vertex.Engine" Version="0.1.0" />
    <None Include="Assets\**" CopyToOutputDirectory="PreserveNewest" />
  </ItemGroup>
</Project>

Run it with dotnet run. The Coin Grab tutorial builds a whole game this way.

2. Editor + C#

The same Bobber component, but the cube and camera are made in the editor:

  1. Make the cube with Create › Cube.
  2. With it selected, choose Add Component in the inspector, type Bobber and pick New Script. The editor writes Assets/Scripts/Bobber.cs, builds it, and adds it to the cube.
  3. Open the file in your code editor and paste in the Bobber class above. Switch back to Vertex: it rebuilds, and keeps your scene as it was.
  4. Height and Speed now show in the inspector. Change them per cube, and press Play.

Public properties with a getter and setter are shown in the inspector and saved with the scene. Slots for other objects, components, prefabs, sounds and materials can be filled by dragging them in. C# scripting covers the rest.

3. Editor + visual scripting

No code: add a Visual Script component to the cube and press New Visual Script. The graph opens in a tab. This one moves the cube up and down a little each frame, following a sine wave, and turns it 90° a second:

Drag across the graph to pan and scroll to zoom. Hover a node to see what it does, and press Run to watch the flow go along the white wires. In the editor the wires light up like this while the game plays. Visual scripting explains events, flow, values and variables.

Mixing them

All three are the same engine, so they combine freely. Some common mixes:

Open a code-only game in the editor

Choose File › Open Project and pick the game's .csproj. The editor makes a .vertexproject beside it, builds the code, and shows the world your Load() builds. Play runs the game as it would run on its own. From there you can make prefabs, materials, scenes and VFX graphs in the editor and use them from code:

public override void Load()
{
    // A level made in the editor, as the whole world...
    Scene.Load("Scenes/Arena.scene");

    // ...or added to one built in code.
    Scene.Active.Add("Scenes/Bonus Room.scene");

    // Copies of a prefab made in the editor.
    Prefab crate = Prefab.Load(Application.AssetPath("Prefabs", "Crate.prefab"));
    for (int i = 0; i < 5; i++) crate.Instantiate(new Vector3(i * 2f, 0f, 0f));

    // Something placed in the editor, found by name.
    GameObject door = GameObject.Find("Door")!;
}

Give an editor game code that runs around its scenes

A game made in the editor doesn't need a Game class. Components on objects do the work. But if you want code that runs for the whole game (setting things up, a timer, cheats), write one that starts in your scene:

public class MyGame : Game
{
    public MyGame() => StartScene = "Scenes/Main.scene";

    public override void Load()
    {
        base.Load();                        // opens the start scene
        Network.GameVersion = "1.0";        // anything else to set up
    }

    public override void Update()
    {
        if (InputSystem.GetKeyDown(Key.F5)) Scene.Load(StartScene!);   // start again
    }
}

The editor still opens the start scene for editing, and Play runs your Load and Update around whichever scene is open, unsaved changes included. A game whose Load builds everything in code (no StartScene) opens with the world it builds instead.

C# and visual scripts together

Objects can have C# components and visual scripts side by side. They can talk to each other:

VisualScript script = door.GetComponent<VisualScript>()!;

// Read and change a visual script's variables.
float health = (float)script.GetVariable("Health")!;
script.SetVariable("Speed", 8f);

// Start "On Event" nodes called "Door Opened" (with a value: here, the door), in every
// visual script in the scene, or just in the ones on one object.
VisualScript.SendEvent("Door Opened", door);
VisualScript.SendEvent("Door Opened", door, to: lever);

Going the other way, visual scripts don't reach into C# components: they read and set other visual scripts' variables (Get Variable On, Set Variable On) and send events. Network events reach both: a C# component's OnNetworkEvent and a graph's On Network Event get the same events. The Duel tutorial uses that so its C# and visual versions can play each other.

Rule of thumb: make places in the editor, and behaviour in whichever you're quickest with. Generated or repetitive things (a grid of tiles, a hundred enemies) are usually shorter in code.
